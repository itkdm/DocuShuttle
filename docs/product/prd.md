# 纸上鸭产品需求（权威版）

状态：V1 Draft
更新时间：2026-08-26

## 一句话定义

纸上鸭是直接理解、生成、修改、检查并交付 Word 文档的 Agent；它围绕真实 DOCX 工作，而不是先生成一段文本再让用户手工粘贴排版。

## 目标用户与任务

第一阶段服务需要按既有格式完成实验报告、作业、申请材料、业务模板和相似结构文档的个人用户。典型任务包括：

- 只有空白模板：理解占位区域并生成完整内容。
- 只有完成示例：保留结构与样式，识别并替换个性化内容。
- 模板加示例：模板结构优先，示例只作为内容和完成度参考。
- 对 Working Document 持续局部修改、重生成图片、恢复版本并导出。

## 核心对象

- **Source Document**：用户上传的模板、示例或辅助资料，保持原始字节不变。
- **Working Document**：当前可编辑文档，指向最新有效的不可变版本。
- **Document Version**：一次导入、用户编辑、Agent 写入或恢复产生的快照。
- **Document Region**：可稳定定位的段落、表格、单元格、图片或结构区域。
- **Proposal / Decision**：Agent 对区域的保留、重生成、待确认或锁定建议，以及用户作出的决定。
- **Agent Run**：从理解到校验的可暂停、可恢复任务，和文档版本不是同一个状态。

## 主流程

1. 用户上传模板、示例或两者，并描述目标。
2. 系统创建任务和 Working Document：有模板时克隆模板；只有示例时克隆示例的原始 OOXML 包。
3. Agent 解析结构与内容，建立稳定区域 ID，提出保留、生成、待确认、锁定范围。
4. 局部低风险建议以内联建议呈现；多区域、删除、结构变化或不确定任务先展示只读计划。
5. 用户批准、拒绝、缩小范围或补充要求。计划绑定基础版本，过期计划不得静默写入新版本。
6. Agent 生成文本、代码、表格内容和候选图片；图片由用户选择后才应用。
7. 每次实际写入前建立检查点，原子提交一个新版本；UI 在提交成功后更新，不把流式 token 直接写入 DOCX。
8. 系统进行结构完整性和可用的视觉检查。失败时保留最近有效版本，并允许重试、跳过可选步骤或回滚。
9. 用户继续自然语言或直接编辑，查看/恢复版本，导出并重新打开 DOCX。

## 交互模型

桌面工作台以中央文档画布为主，左侧为可折叠结构/区域导航，右侧为可折叠 Agent、计划、任务进度和恢复操作。建议直接投射到文内，聊天不与文档割裂。

移动端第一阶段支持查看、提问、审批、重试、版本和下载，不承诺完整精密排版编辑。

## HITL 规则

以下情况必须先确认：多区域修改、删除、结构/分页风险、同时生成多类资产、低置信度判断、范围含糊的“全部优化”。锁定区域不允许 Agent 写入。

局部建议支持逐项或批量接受/拒绝、重新生成、保留原文后插入、替换原文。任何确认都绑定 `base_revision`；版本变化后返回冲突并重新分析。

## MVP 范围

必须支持：

- `.docx` 模板/示例上传与任务创建；
- 稳定区域身份与段落/表格/图片级选择；
- Agent 分析、计划、HITL、文本和图片生成；
- Working Document、多轮修改、不可变版本、恢复和导出；
- 真实阶段进度、取消、失败恢复和活动记录；
- 匿名 Supabase Auth 用户与数据隔离；
- 真实 DOCX 结构及重开回归验证。

明确延期：多人实时协作、完整移动端排版、旧 `.doc`、PDF 原生编辑、宏文档、企业权限体系、模板市场和计费。

## 成功标准

- 用户无需复制粘贴即可从输入文档得到可继续编辑和导出的 Working Document。
- Agent 准确说明作用范围，未经批准不执行高风险写入。
- 任意失败不会损坏最近有效版本，刷新或重连可恢复真实任务状态。
- 导出 DOCX 无修复提示；非目标 OOXML 部件无未解释变化；目标区域修改精确。
- 五类核心验收案例全部在浏览器、API、数据库、对象存储和导出文档层面通过。

## 交互研究依据

交互模式参考当前官方公开能力进行抽象，不复制其品牌视觉：Microsoft Copilot in Word、Google Docs with Gemini、Notion Agent/Plan mode、Gamma 版本和模板说明。具体链接和设计结论随实现 ADR 维护。
